## 1. Цель и горизонт

- **Сейчас:** синглплеер.
- **Через 1–2 месяца:** кооп на 2–4 игрока, два клиента видят друг друга в тестовой сцене. Не полноценный кооп — только база.
- **Потом:** выделенный сервер, PvP, 10–20 игроков.
- **Платформа:** Steam/PC.

---

## 2. Фреймворк

**Выбран: NGO (Netcode for GameObjects) + Unity Relay (join code)** — для коопа.

- Steam-лобби — позже, когда базовая сеть заработает.
- Mirror — не выбран: лишние сторонние слои (Mirror + Steamworks.NET + FizzyFacePunch) на новом проекте.
- FishNet — не выбран: избыточен для 2–4 игроков.

> Финальное решение по фреймворку подтверждается в чате перед подключением. До этого — только «сетевая гигиена» без сети.

---

## 3. Стратегия (три этапа)

1. **Сейчас — «сетевая гигиена» без сети.** Аудит + развязка синглтонов через интерфейсы/события. Никакого NGO-кода, пока аудит не закончен.
2. **Потом — кооп на NGO.** 2–4 игрока, два клиента видят друг друга, базовая синхронизация (позиция, инвентарь, урон).
3. **Потом — dedicated / PvP.** Выделенный сервер, 10–20 игроков, Steam-лобби, античит.

**Запрещено до окончания аудита:**
- Подключать NGO/Relay кодом.
- Переписывать `PlayerProgress` / `InventoryManager` до разметки.
- Начинать Steam-интеграцию (только Relay join code, и то после аудита).

## 4. Метод аудита (для каждой системы)

Три вопроса:

- **А. Что при одновременном действии двух игроков?** (гонки, lost update, двойной спавн)
- **Б. Может ли клиент соврать?** (публичные методы, прямые поля, отсутствие валидации)
- **В. Насколько критична задержка?** (высокая / средняя / низкая)

**Разметка:** сервер-авторитарно / клиент + валидация сервера / косметика (клиентски).

**Правило:** если система даёт преимущество одному игроку (урон, ресурсы, позиция в бою) — сервер-авторитарна; если только для глаз — клиентская.

**Проверка аудита:** «Если запустить два клиента и один начнёт читерить (телепорт, дюп, ваншот), какой мой код это остановит?» Если «никакой» — система должна быть сервер-авторитарной, но не готова → в `07-refactor-checklist.md`.

## 5. Глоссарий

| Термин | Значение |
|---|---|
| **ServerRpc** | Клиент → сервер. Запрос на действие. Сервер решает, применять ли. |
| **ClientRpc** | Сервер → клиенты. Рассылка события/эффекта (анимация, цифры, звук). |
| **NetworkVariable** | Реплицируемое поле. Сервер пишет, клиенты читают. |
| **NetworkTransform** | Репликация позиции/поворота. |
| **NetworkAnimator** | Репликация параметров аниматора (Speed, IsMoving, триггеры). |
| **CombatMember** | Атрибуция урона: `Player`, `Wild`, `Tamed`, `Mounted`, `OtherPlayer`, `OtherTamed`. |
| **Server-authoritative** | Сервер решает, клиент только просит. |
| **Client-predicted** | Клиент показывает сразу, сервер корректирует (откат при отказе). |
| **Косметика** | Только для глаз: цифры урона, партиклы, анимации. Не влияет на состояние мира. |
| **Гонка (race)** | Два клиента одновременно меняют одно состояние → lost update / двойной эффект. |
| **Идемпотентность** | Повторный вызов не меняет результат (важно для `Die()`, `KnockOut()`). |

**Почему такой порядок:**
- **1–2** — самые частые операции (предметы, урон), дают максимальный эффект от развязки.
- **3** — фундамент коопа: `PlayerProgress.Instance` → per-player. Без этого остальные системы не развести.
- **4** — позиция/движение: клиент-предсказание, `NetworkTransform`.
- **5** — мир/строительство: серверные структуры, снапы.
- **6** — существа/AI: серверный AI, `NetworkAnimator`, репликация позиций.
